# HotM 2026.5.9

**Release date:** 2026-05-11
**Type:** Patch — fixes two response-shape mismatches caught in v2026.5.8 smoke test.

[Epic #202](https://git.integrolabs.net/Fortemi/HotM/issues/202) landed in v2026.5.8 and a live install smoke test surfaced two bugs where the UI types didn't match the Fortemi server's actual response shape. The features themselves work end-to-end after these fixes.

## Install

### Linux (one command)

```bash
curl -fsSL https://raw.githubusercontent.com/Fortemi/HotM/main/scripts/install.sh | bash
```

### Linux (.deb direct)

```bash
sudo apt-get install ./HotM_2026.5.9_amd64.deb
```

### macOS

```bash
hdiutil attach HotM_2026.5.9_aarch64.dmg
cp -R "/Volumes/HotM/HotM.app" /Applications/
hdiutil detach "/Volumes/HotM"
xattr -cr /Applications/HotM.app
```

### Docker UI image

```bash
docker pull ghcr.io/fortemi/hotm-ui:2026.5.9
```

## What changed

### Fixed

- **`InferenceConfig.embedding_backend` was typed as a bare string** when the server actually returns it wrapped as `AttributedValue<string>` — `{ source, value }`. Every other config field (Ollama URL, OpenAI key, etc.) follows the wrapped pattern; `embedding_backend` does too. Without the fix, hydrating a server-set override stored the entire wrapper object as the form's selected backend, producing an unselected dropdown after `getConfig()`. The type is now `AttributedValue<string> | null`; hydration reads `.value`; the dirty-check + buildUpdate compare against `.value` (or `null` when absent). The POST request body shape stays a bare `string | null` per the Fortemi tri-state spec.

- **`POST /inference/config` returns `{ current, previous, status, warnings }`** but the UI was typed and coded for a bare `InferenceConfig`. All four save modes (plain, validate, atomic, dry_run) share the envelope shape; `current` is the new effective config, `previous` is the pre-change snapshot. The UI now reads `result.current` after save, and shows `result.warnings` in the success toast — important for per-archive saves where Fortemi attaches the deferred-hot-swap notice as a warning. The dry-run modal also uses `result.previous` for its "current" panel (the unchanged server state) and `result.current` for the "would be" panel.

- **`updateConfig` return type** is now `Promise<UpdateConfigResponse>` instead of `Promise<InferenceConfig>`. `updateConfigValidated` (already marked `@deprecated`) updated to match. No call site outside `InferenceSettings.tsx` consumed the return value, so this is a non-breaking tightening.

### Verification

Live smoke test against the Fortemi v2026.5.6 sidecar bundled in v2026.5.8/v2026.5.9:

- `GET /api/v1/inference/config` returns the wrapped `embedding_backend` after a `POST` with `{ embedding_backend: "ollama" }` — confirmed via curl.
- `POST /api/v1/inference/config?dry_run=true` returns `{ current, previous, status: "dry_run", warnings: [] }` with `current === previous` (nothing applied).
- `GET /api/v1/inference/config/audit` returns `{ entries: [...] }` matching the existing UI types — confirmed entries appear after a POST changes config.
- `npm run typecheck` clean.
- `npm test -- --run`: **1427 / 1427 passing**.

## Compatibility

No breaking changes to component props or API entry points. Type tightening only on the `updateConfig` return type — the field shape on `InferenceConfig.embedding_backend` widens slightly (was `string | null`, now `AttributedValue<string> | null`) but no consumer outside `InferenceSettings.tsx` reads it. Sidecar dependency unchanged: Fortemi v2026.5.6.

Pairs with [HotM v2026.5.8](https://github.com/Fortemi/HotM/releases/tag/v2026.5.8) (the epic #202 landing).

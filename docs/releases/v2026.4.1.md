# HotM 2026.4.1

**Release date:** 2026-04-29
**Type:** Patch — bug fixes only, no breaking changes

This patch addresses two issues discovered during desktop install validation against v2026.4.0. Both are user-visible blockers for first-run experience on Linux; macOS users hit the bundling issue but not the request-body issue (the wire-level mechanism differs).

## What's fixed

### 🐛 Admin Panel "Test Connection" no longer fails on a healthy backend

In v2026.4.0, clicking **Admin → Inference → Test Connection** returned `Connection Failed: Bad Request` even when Ollama and the bundled matric-api sidecar were both running and reachable. Same story for note creation, configuration writes, and any agent tool call that carried a JSON body — all of them hit the backend with `Content-Type: application/json` and zero bytes of body.

Root cause: Tauri v2 defaults command-argument deserialization to camelCase. The `hotm_fetch` Rust handler accepts a snake_case `body_b64: Option<String>`, but the documented `HotmHostAdapter` contract and the auto-injected `__HOTM_HOST__.network.fetch` adapter both send the body as `body_b64`. Tauri silently dropped the unrecognized snake_case key, so `hotm_fetch` received `body_b64: None` and reqwest produced a body-less request. GET requests were unaffected.

Fix: `#[tauri::command(rename_all = "snake_case")]` on `hotm_fetch`, so the documented snake_case JS contract works end-to-end. One-line change in `ui/src-tauri/src/lib.rs`.

### 📦 Bundled sidecar moved to a HotM-namespaced path (closes [#187](https://git.integrolabs.net/Fortemi/HotM/issues/187))

The Tauri-bundled Fortemi sidecar binary now installs as **`hotm-matric-api`** instead of `matric-api`:

| Platform | Path |
|---|---|
| Linux (.deb / AppImage) | `/usr/bin/hotm-matric-api` |
| macOS | `HotM.app/Contents/MacOS/hotm-matric-api` |
| Windows | `hotm-matric-api.exe` alongside `hotm.exe` |

This eliminates the `/usr/bin/matric-api` collision with sibling Tauri apps that bundle their own copy of `matric-api` (e.g., `bt6-arsenal`). Installing HotM v2026.4.1 alongside such a package no longer requires `dpkg --force-overwrite`.

The upstream Fortemi sidecar release artifact name (`matric-api-<triple>`) is unchanged — only the staged-into-the-bundle name changes; CI workflows rename at stage time.

## Upgrade notes

### Linux

If you previously installed v2026.4.0 and used `dpkg -i --force-overwrite` to resolve a conflict with another package that also shipped `/usr/bin/matric-api`:

```bash
sudo apt-get install ./HotM_2026.4.1_amd64.deb
```

This installs cleanly because the bundled sidecar now uses the new `hotm-matric-api` path. **After the upgrade, `/usr/bin/matric-api` is no longer present** (it was owned by hot-m and is removed as part of the v2026.4.0 → v2026.4.1 file-list change). If you need the old path back for the sibling app whose ownership you previously overwrote, reinstall it:

```bash
sudo apt-get install --reinstall <sibling-package>
# e.g.: sudo apt-get install --reinstall bt6-arsenal
```

After that, both apps coexist cleanly: hot-m owns `/usr/bin/hotm-matric-api`, the sibling owns `/usr/bin/matric-api`, no overlap.

### macOS

DMG drop-in replace as usual. The internal binary path inside the .app changes from `Contents/MacOS/matric-api` to `Contents/MacOS/hotm-matric-api`; this is invisible to end users.

### Windows

NSIS installer drop-in replace. The bundled sidecar is now named `hotm-matric-api.exe` alongside `hotm.exe`.

### MCP / agent integrations

If you have any MCP client config or scripts that explicitly reference the bundled sidecar binary path, update them:

| Old | New |
|---|---|
| `/usr/bin/matric-api --mcp` | `/usr/bin/hotm-matric-api --mcp` |
| `/Applications/HotM.app/Contents/MacOS/matric-api --mcp` | `/Applications/HotM.app/Contents/MacOS/hotm-matric-api --mcp` |
| `pkill -f matric-api` | `pkill -f hotm-matric-api` |

(See `docs/operations/agent-guide.md` for current paths.)

## Open follow-ups

- **#187 partial fix only**: the sidecar still lives under `/usr/bin/` rather than the Debian-Policy-recommended `/usr/lib/hot-m/` private path. Full relocation requires Tauri's `externalBin` mechanism to support private install paths and is tracked separately.
- **#186 (default model drift) remains open** pending decision on whether the matric-api default should track the newer Qwen3.5 family (matching scripts) or stay on Qwen3:14b (matching v2026.4.0 release notes). See [issue #186](https://git.integrolabs.net/Fortemi/HotM/issues/186) for the three-option analysis.
